## 開発ワークフロー（厳守）

- `index.html` は**生成物**。編集は `build/` 配下のみ。結合:
  ```
  cat build/00-head.html build/10-core-a.js build/11-core-b.js build/12-core-c.js build/20-app.js > index.html
  ```
- `node tests/run.js` が **0 failed** になるまでコミット禁止
- コミット: メッセージ先頭 `Round N:`（FEATURE_AUDIT §0 の「次の通し番号」）、末尾にテスト数と `0 failed`
- 既存テストが割れたら: そのテストのウィンドウ/パターンを実態に合わせて更新し、コメントに `RoundXXXで更新` を残す（**テストを緩めて通すのは禁止**）
- **毎ラウンド FEATURE_AUDIT を更新**（§2へ行追加・ヘッダのテスト数と次番号）
- ブランチは `claude/product-swot-analysis-bozq7s`。公開ブランチは `main`（同一コミットへ両方push）

## 確立済みの監査方法論（このセッションで実証済み・実績順）

1. **兄弟コードパス比較** — 構造的に類似する2〜3のパスを横並びにし、片方だけ欠けている処理（ガード/aria/検証/スナップショット）を探す。最多の実績（Round 491/492/495/497/498/499/502/504/510 等）
2. **サブシステム全行通読** — grepではなく対象機能の**全行**を読む。本セッション最重要のバグ（Round 505 atlas破損・506 glTF違反・507 Caps Lock）はすべてこの方法で発見された
3. **アドバーサリアル検証** — 発見は複数の**反証専門**視点で検証してから実装。「もっともらしいが誤り」の排除に有効（Round 506–508 はこの多視点検証を通過）
4. **外部一次ソース照合** — RANKS等の外部由来データは WebFetch で一次ソースと直接照合（Round 494 で欠落カテゴリを発見）
5. **空検証の警戒** — 「CSSルールの文字列が存在する」だけのテストは対象への到達性を検証していない。テストは**実マークアップ/実バイト**に対して書く（Round 496/497/511 の教訓）

## 品質基準（重要）

- **弱い発見を無理に修正しない**。clean sweep（実害バグなし）は正直にそう報告する。それは価値ある結果
- **予防的修正**（実害が未発生のドリフト対策等）は FEATURE_AUDIT にその旨を明記する（Round 503/511 の前例）
- 視覚品質に関わる**形状/テクスチャ変更は、視覚検証体制が無い限り凍結**（§3-1 の理由）。数値バグ（NaN/範囲/バイナリパッキング）は視覚検証と無関係に安全に修正できる
